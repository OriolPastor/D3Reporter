# Alert Rules for Disguise Network Monitor

This file defines the conditions under which the monitor (`alert.py`) must emit an alert. The script reads `status.json` (generated by the WebSocket service) and checks these rules.

## Priority Levels
- **Critical** – Immediate action required (show may be affected).
- **High** – Degraded performance, needs attention soon.
- **Medium** – Informational, monitor trends.

## 1. Critical Alerts (Priority 1)

| Condition | Trigger | Output message |
|-----------|---------|----------------|
| Director disconnected | `websocket_state == "disconnected"` for more than 5 seconds | `CRITICAL: Director lost connection` |
| Playback stopped unexpectedly | `playback_state == "stopped"` when it should be "playing" | `CRITICAL: Playback halted on $server` |
| Sync lost (Genlock/Framelock) | `sync_status != "locked"` on any Actor server | `CRITICAL: Sync lost on $actor` |
| FPS below minimum | `fps < 24` sustained for 5 seconds | `CRITICAL: Low FPS ($fps) on $server` |

## 2. High‑Priority Alerts (Priority 2)

| Condition | Trigger | Output message |
|-----------|---------|----------------|
| High CPU usage | `cpu_usage > 80%` sustained for 10 seconds | `HIGH: CPU at $cpu% on $server` |
| High GPU usage | `gpu_usage > 90%` sustained for 10 seconds | `HIGH: GPU at $gpu% on $server` |
| Temperature too high | `temperature > 85°C` | `HIGH: Temperature $temp°C on $server` |
| Frame drop rate | `frame_drop_rate > 1%` over 1 minute | `HIGH: Frame drops $drop% on $server` |
| Reconnection attempts | `reconnect_attempts > 3` in the last minute | `HIGH: Unstable connection ($attempts reconnects) on $server` |

## 3. Medium‑Priority Alerts (Priority 3)

| Condition | Trigger | Output message |
|-----------|---------|----------------|
| High memory usage | `memory_usage > 90%` | `MEDIUM: Memory at $mem% on $server` |
| Network latency | `latency_ms > 50` (in LAN) | `MEDIUM: High latency ($latency ms) to $server` |
| Asset load errors | `asset_errors > 0` | `MEDIUM: Asset load errors on $server` |
| Active layers anomaly | `active_layers_count` deviates significantly from expected baseline | `MEDIUM: Unusual layer count ($count) on $server` |

## Implementation Notes for `alert.py`

- The script should be executed by OpenClaw every 30 seconds.
- It must read `status.json` from a known location (use relative path or environment variable).
- For conditions that require sustained values (e.g., CPU > 80% for 10 seconds), keep a small buffer of previous readings (last 3‑5 checks) before raising an alert.
- Alerts should be printed to stdout in plain text. OpenClaw will forward them to Telegram.
- Avoid alert spam: if a condition persists, send at most one alert every 5 minutes (implement cooldown).
- During the first 30 seconds after the monitor starts, ignore all alerts to avoid false positives during stabilization.
